# M1 delivery proof

Issue: [#352](https://github.com/ishtms/faultlane/issues/352)

Status: Approved on August 15, 2026. Track the seven authoritative documents using option 1 below.

## Outcome

M1 changes cannot merge unless the supported Windows path, Linux canonical check, dependency checks, and a real browser setup flow pass. Fuzz targets compile in the canonical check and run in a short recurring campaign. Doctor reports missing browser prerequisites accurately. Completed plans leave the active queue. Product and architecture decisions have one reviewable authority.

## Context and evidence

The current implementation has useful checks, but their enforcement is inconsistent:

- `.github/workflows/ci.yml` runs `check` on Ubuntu and `windows check` on `windows-2025`.
- Main ruleset 20747299 requires only `check`, `dependency audit`, and `dependency review`. It does not require `windows check`, even though Windows UE 5.8 is the supported development target.
- `scripts/check-fast` runs Rust formatting, Clippy, workspace tests, web formatting, lint, and type checking. `scripts/check` adds release Rust and production web builds.
- The three tracked fuzz binaries under `fuzz/fuzz_targets` are excluded from the Cargo workspace and are not compiled by either canonical check.
- The tracked Playwright setup and dashboard tests run only from the Windows-oriented isolated proof or by direct command. Pull request CI does not execute a browser flow.
- `scripts/doctor` checks command availability, Docker, Compose, and ports, but not the installed Playwright package or configured Chrome executable.
- `docs/plans/active/README.md` says merged plans move to completed. Plans 298, 299, 300, 311, and 346 remain active after their changes merged.
- `AGENTS.md` declares `docs/product/overview.md`, `PRD.md`, and `ARCHITECTURE.md` authoritative. Those files are ignored and not tracked, and their local copies disagree with the tracked repository and GitHub roadmap.

The current source policy cannot be repaired silently. Repository instructions prohibit changing `.gitignore`, force-adding ignored Markdown, and staging `AGENTS.md`. One narrow exception is required before the authority repair can be implemented.

The ignored authority set is exactly `docs/product/overview.md`, `PRD.md`, `ARCHITECTURE.md`, `docs/architecture/index.md`, `docs/security/threat-model.md`, `docs/operations/deployment.md`, and `docs/operations/rollback.md`. `docs/security/processor-boundary.md` and `docs/operations/isolated-worker.md` are already tracked and must not be duplicated or re-added.

## Acceptance criteria

- The live main ruleset preserves its current protections and strict checks, then additionally requires the exact `windows check` and `browser check` contexts.
- A repository script starts isolated PostgreSQL, MinIO, API, ingest, and production web services on non-default ports, runs `scripts/smoke`, executes `apps/web/e2e/setup.spec.ts` in Chrome, and removes its dedicated containers, network, volumes, processes, logs, and temporary data on success or failure.
- Pull requests and pushes to `main` run the browser script in an unprivileged Ubuntu job with no repository or production secrets.
- `scripts/check-fast` compiles all tracked fuzz binaries through `cargo check --manifest-path fuzz/Cargo.toml --bins` on Linux and Windows.
- A scheduled and manually dispatchable workflow uses a pinned nightly toolchain and pinned `cargo-fuzz`, runs each target with a fixed per-target wall-time budget, and fails with useful logs when a crash is found.
- `scripts/doctor` exits nonzero with an actionable fixed message when the workspace Playwright dependency is unavailable or the Chrome executable selected by the Playwright configuration is missing.
- Plans 298, 299, 300, 311, and 346 move to `docs/plans/completed`, retain their history, and record the merged PR and final verification outcome.
- The selected source-of-truth option removes the current contradiction without creating a second product or architecture authority.
- Existing canonical commands, setup APIs, product behavior, data, tenant boundaries, and runtime feature flags remain compatible.

## Risk and blast radius

Risk: R3.

The repository-script changes are reversible, but the ruleset update changes what can merge to `main`. A wrong context name could block every pull request, while accidentally replacing rather than extending the rules could weaken branch protection. Browser CI executes services against synthetic local data and must not receive production credentials. Fuzzing consumes untrusted generated bytes and must remain time and resource bounded.

No production deployment, customer data, database migration, runtime dependency, product API, billing behavior, authentication behavior, or destructive data operation is in scope.

## Selected design

### Canonical and recurring checks

Keep `scripts/check` as the canonical build and test entry point. Add fuzz-target compilation to `scripts/check-fast` so both Linux and Windows exercise it without requiring nightly Rust.

Add one focused browser proof script rather than putting service orchestration inside YAML. The script owns unique Compose project names, non-default ports, readiness waits, process identities, canonical smoke, the setup Playwright spec, captured safe logs, and cleanup. The CI job installs existing locked dependencies, creates a development-only `.env`, and calls that script.

Keep time-bounded mutation fuzzing out of every pull request to avoid nondeterministic latency. Run it weekly and on manual dispatch. Use one pinned nightly job that executes all three existing targets sequentially with fixed wall time, no external services, no credentials, and no network-dependent corpus.

### Doctor

Use the existing locked web dependency to resolve Playwright and its configured Chrome executable. Doctor remains read-only. Missing Node packages or browser files increment the same failure counter and print an install command that matches the repository setup.

### Ruleset

Read ruleset 20747299 immediately before mutation. Preserve deletion protection, non-fast-forward protection, linear history, squash-only pull requests, review-thread resolution, strict checking, and the three existing required contexts. Add only `windows check` and `browser check`. Read the ruleset back after mutation and compare every rule and required context.

Do not add a bypass actor or weaken a current protection. If either new job is unavailable after rollout, revert the repository change first or remove only that exact new context so `main` is not indefinitely blocked.

### Plans and authority

Move each merged tracked plan with Git rename semantics and append its merged PR and final outcome. Do not rewrite historical reasoning.

The product and architecture source repair depends on the explicit decision below. No workaround using a new filename or another duplicate document is acceptable because `AGENTS.md` would still point reviewers at stale ignored files.

## Security analysis

| Risk | Control | Evidence |
|---|---|---|
| Pull requests can bypass Windows behavior | Require the exact successful `windows check` context with strict base synchronization | Ruleset readback and a test PR |
| Wrong ruleset update weakens protection | GET, minimally edit, PUT, then compare all preserved rules and contexts | Before and after JSON captured in the plan proof |
| Browser CI receives secrets | Use only checked-in development defaults and synthetic local data with read-only repository permissions | Workflow permissions and captured process environments |
| Browser services leak between jobs | Unique project names and ports plus validated cleanup in a trap | No matching processes, containers, networks, or volumes after success and forced failure |
| Generated fuzz input escapes its boundary | No credentials or services, fixed target list, fixed time budgets, existing parser limits | Scheduled workflow logs and local one-target proof |
| Doctor exposes private paths | Fixed messages name the missing component and install command, not resolved home or cache paths | Behavior tests for missing package and browser cases |
| Stale local docs override reviewed decisions | Select and enforce one tracked authority | Repository check and source-policy review |

## Verification and operations

Required local evidence:

- `bash scripts/doctor` succeeds with the installed package and Chrome and fails safely when either is intentionally hidden.
- `bash scripts/check-fast` compiles all fuzz bins in addition to existing gates.
- `bash scripts/check` remains the same complete release gate.
- The browser proof prints `smoke checks passed`, passes the setup Playwright spec, and leaves no owned resources.
- A forced browser failure returns nonzero and still leaves no owned resources.
- One fuzz target completes its fixed time budget without a crash; a deterministic crash fixture proves nonzero failure reporting if a safe existing harness permits it.
- Linux `check`, Windows `windows check`, browser `browser check`, dependency audit, and dependency review pass on the final pull request.

Operational evidence:

- Capture the ruleset before and after JSON outside the repository and compare rule types, merge methods, strictness, bypass actors, and required contexts.
- Confirm a new test pull request reports all five required contexts and cannot merge while one is pending.
- Confirm scheduled fuzz can also be dispatched manually and does not require repository secrets.

## Compatibility, rollout, and rollback

The check and doctor changes are additive. Existing commands keep their names. The browser and fuzz jobs use existing code and development-only infrastructure. There is no stored-data or API compatibility impact.

Merge repository changes before requiring their contexts. Confirm the jobs complete successfully on `main`, then add the required contexts. Never require a context that has not reported for the repository.

Rollback in this order:

1. If a new required context is unavailable, remove only `browser check` or `windows check` from the ruleset while preserving all existing protections.
2. Revert the workflow and script commit through a pull request.
3. Keep completed plans archived and keep the approved authority unless that authority itself was proven wrong.
4. Do not bypass rules, push directly to `main`, delete test evidence, or change product data.
